# Contributing

kjk is written mostly by LLM agents, directed and reviewed by the
maintainer, who makes the decisions. This file is for anyone else working
in the repository, by hand or with an agent of their own.

## Getting started

1. Build and run it as [`README.md`](README.md) says ("First run").
2. Install the pre-commit hook, once per clone:

   ```bash
   cargo xtask hooks
   ```

3. Read, in this order: [`AGENT.md`](AGENT.md) (the rules that never bend,
   the gate, parallel work), [`docs/INDEX.md`](docs/INDEX.md) and the doc
   for the area you touch. [`ROADMAP.md`](ROADMAP.md) holds the why: the
   goals, principles and decisions. [`QUIRKS.md`](QUIRKS.md) lists the
   reference bugs we keep on purpose; check it before "fixing" one.

[`CONTEXT.md`](CONTEXT.md) is the maintainer's own workflow (the journal
under `context/`, slices). You do not need it to change the runtime.
`context/` is the maintainer's local, untracked research folder: links
into it from the docs point at files you will not have.

## The rules that never bend

The full list is in `AGENT.md`. The ones that bite first:

- **No game data, ever**: not in commits, issues, pull requests, tests or
  screenshots of extracted files. Test fixtures are data we make ourselves.
  The pre-commit hook (`cargo xtask publish-check`) refuses the shapes it
  knows; it cannot catch everything.
- **Game installs are read-only.** Nothing writes into them.
- **Machine paths live in `.env`**, never in code or docs.
- **Reference code is read, not copied.** reone, xoreos and OpenJK are GPL;
  kjk is MIT. Describe the behaviour you match in your own words and
  show that ours matches it. No original addresses or decompiler names
  (`FUN_…`).
- **The games' own rules first.** Behaviour comes from the games' scripts
  and data and what the executables do, made to work for every module at
  once. No per-module patches, no rewriting a game's script logic natively.
  Survey every rule the reference applies to an area before building it.

## Licensing

kjk is MIT ([`LICENSE`](LICENSE)), and so is every contribution: by
opening a pull request you agree to license your change under it.

- **Never copy or translate code from a GPL project** (OpenJK, Quake III,
  reone, xoreos), not even a line, a table or a constant's name. Read them
  for behaviour only, write down what the behaviour is in your own words,
  and write our code from that description.
- Their identifiers stay out of our code and docs (`PM_…`, `WP_…`,
  `saberMoveData`, `pmove_t`, …), and so do phrases such as "port of" or
  "adapted from" next to their names. `cargo xtask publish-check` refuses
  these shapes; the few places that may name a reference project are on
  its allow-list.
- A new dependency must carry a licence on the accepted list in
  [`deny.toml`](deny.toml) (`cargo deny check licenses`). Binary releases
  ship `THIRD-PARTY-LICENSES.html`, generated by `cargo about` from
  [`about.toml`](about.toml).

## Branches and pull requests

- Never commit to `main`. Work on a branch named `<you>/<topic>`, ideally
  in its own git worktree (`docs/BUILD.md` on seeding its `target/`).
- Open a pull request against `main`. CI runs two jobs: **tests**
  (publish check, fmt, the approved tests) and **clippy** (both lints).
- The maintainer reviews and merges.
- Pushed history is never rewritten. To catch up with `main`, merge it into
  your branch.
- Commit messages say the effect in plain words ("Silent shouts carry only
  as far as a creature hears"), not the files touched.

## The gate, before every commit

From the repository (or worktree) root:

```bash
cargo fmt --all -- --check \
  && cargo clippy -q --workspace --all-targets --all-features -- -D warnings \
  && cargo test --release -p approved_tests
```

A change to what the verbs share with play also gets
`cargo clippy -q -p launcher --all-targets --no-default-features -- -D warnings`.
`cargo test --release -p approved_tests --features rig` adds the skeleton
jolt ceilings, which need the game installs. Write files with LF endings.

## Tests, probes and the sim hash

- **Permanent tests live only in `crates/approved_tests`**, and only for
  scenarios the maintainer approved by name ([`docs/TESTS.md`](docs/TESTS.md)).
  Checks you want while working are probes (`kjk sim probes`, `kjk combat …`,
  `kjk script …`), not new `#[test]`s.
- **The sim is deterministic** and its final hash after a fixed run is
  pinned as `KJK_SIM_HASH` in `.github/workflows/ci.yml` and `manual.yml`.
  It moves only on purpose, and only the merge pins it: say why in
  `bumps/<branch>.toml` (`sim = "…"`) and in the pull request
  ([`bumps/README.md`](bumps/README.md)).
- **Snapshot, save and recording formats** carry version tags (KJKS, KJKV,
  KJKR, …). When you change one, don't edit its number: add its history
  line under `[formats]` in the same bump file, and the merge numbers it.

## Walkthroughs

The campaign is played headless as a chain of routes
([`docs/PLAYTESTS.md`](docs/PLAYTESTS.md)). While working, replay the route
your change touches from its checkpoint (`kjk chain k1 ROUTE --alone`).
Before a merge, run `kjk chain k1` from the first route your change can
reach; after any change to the sim or the playthrough harness, the whole
chain to both endings (an unchanged sim hash proves nothing about the
chain). A run stops at its first block. Never rerun a blocked route on an
unchanged build: the sim is deterministic, so it blocks the same way (the
chain's cache answers such a rerun without playing it). A route that blocks
is fixed by the rule that let it happen, with a probe, never by editing the
route around it.

## Quirks

A reference bug we reproduce gets an entry in `QUIRKS.md`. Ask the
maintainer for a range of numbers before adding one; never take the next
free number, since parallel branches collide on it.

## Working with an agent

`AGENT.md` is written for agents and applies to yours. A new worktree's
`target/` can start as a clone of the main checkout's (`docs/BUILD.md`). Long builds and playthroughs
run in the background; never poll them in a loop. Agents never push to or
merge into `main`.

## Bug reports

Check [`KNOWN-ISSUES.md`](KNOWN-ISSUES.md) first; what is listed there is
known. A useful report contains:

* the commit;
* OS and GPU;
* which game's data (KOTOR 1, KOTOR 2 or Jedi Academy; Steam, GOG or disc)
  and which module;
* the steps, and what happened instead; the run folder under
  `kjk-artifacts/runs/` if there is one.

Do not attach your `.env`, a memory dump, or any game file.
